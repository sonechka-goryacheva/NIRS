# Отчёт: поисковый индекс BM25 для справочника IT-команд

По «Методическим указаниям к НИРС (ОАД)», МГТУ им. Н. Э. Баумана, 2026. Реализован этап поиска (retrieval) схемы RAG:
собственный обратный индекс и ранжирование BM25, тестовый набор запросов, метрики Recall@k и MRR.
Все числа ниже воспроизводятся командой `python -m rag eval --details --compare` из корня репозитория;
прогоны «до» и «после» дополнения тегов сохранены в `rag/results/`.

## 1. Корпус и документ

- **Корпус** — 149 команд в 8 категориях (`data/corpus/*.json`): Linux 30, Git 22, PowerShell 22, SQL 17, Сеть 16,
  Docker 15, macOS 15, Python 12.
- **Документ** (индексируемая единица) — одна команда. Так совпадают единица поиска и единица ответа: чат показывает
  карточку одной команды. Разбивать команду на части нет смысла (она короткая), объединять — тоже (ответ стал бы неточным).
- **Индексируемые поля:** `name` + `command` + `description` + `tags`. Поле `examples` не индексируется: примеры почти дословно
  повторяют `command` и лишь удваивают его TF (эксперимент в разделе 4 — без выигрыша).
- После предобработки: словарь |V| = 739 термов, средняя длина документа avgdl = 16 термов (от 11 до 23).
  Матрица «документ × терм» заполнена на 1,5 % (1 651 из 110 111 ячеек) — векторы документов действительно разреженные.

## 2. Предварительная обработка и её обоснование

Одна и та же цепочка применяется к документам и к запросам (замечание 1.1 методички) — `rag/text.py`:

    текст → нижний регистр, «ё»→«е» → токены [a-zа-я0-9]+ → лемма (русские слова) → удаление стоп-слов → термы

Пример (`python -m rag search "посмотреть запущенные контейнеры" --explain`):

    Токены: ['посмотреть', 'запущенные', 'контейнеры']
    Леммы:  ['посмотреть', 'запустить', 'контейнер']

**Регистр и «ё».** Команды пишут по-разному (`Get-Process` / `get-process`, «ещё» / «еще»); различие регистра в этой задаче
не несёт смысла, поэтому текст приводится к нижнему регистру.

**Токенизация — по словам, разделитель — любой символ, кроме букв и цифр.** Запросы — короткие фразы, а смысл несут
отдельные слова. Важный случай — команды: `du -sh <path>` → `du, sh, path`; `Get-Process` → `get, process`;
`docker-compose` → `docker, compose`. Поэтому запрос «что делает du -sh» находит `du -sh` первым (оценка 10,5 против 0 у остальных),
а слово `process` из PowerShell-команды совпадает с тегом `process`. Флаги (`-sh`) теряют дефис, но остаются отдельным
термом. N-граммы и подсловные токены не нужны: корпус маленький, а словоформы снимает лемматизация.

**Лемматизация — pymorphy3 (словарный морфоанализатор), только для кириллицы.** Русский язык сильно флективен: «папка /
папки / папок», «запущенные → запустить», «контейнеры → контейнер». Без лемматизации запрос и документ совпадают только
в одинаковой форме слова. Выбран словарный лемматизатор, а не стемминг (Snowball): он даёт настоящую начальную форму
и не склеивает разные слова по общему префиксу; в корпусе мало текста, и каждая ошибка нормализации заметна.
Латиница (имена команд, английские теги) **не лемматизируется и не стеммится**: `ls`, `ps`, `logs`, `status` — это имена
команд и флагов, их нужно сравнивать точно (английский стеммер Портера превратил бы `status` в `statu`).
Берётся самый вероятный разбор pymorphy3 (без учёта контекста) — для коротких запросов этого достаточно.
Эффект: без лемматизации MRR падает с 0,777 до 0,716, Recall@5 — с 0,555 до 0,465 (раздел 4).

**Стоп-слова — служебные слова и «связки» запросов** (`как, что, для, в, на, с, нужно, сделать, команда…`, `rag/text.py`).
Пользователи пишут «как сделать…», «команда для…», а такие слова не говорят, какая нужна команда. Решающий довод — ответ
«ничего не найдено»: без стоп-слов запрос «рецепт борща со сметаной» находит `git bisect` (через «со»), а «погода в Москве
на выходные» — `df` (через «на»): отсеиваются только 3 из 7 запросов не по теме, со стоп-словами — 7 из 7.
Правило продукта — «случайные команды не показываются» (spec/product/answer_format.md). MRR без стоп-слов на 0,016 выше
(0,793), но Recall@3/@5 ниже, а ложные ответы на посторонние запросы недопустимы — стоп-слова оставлены.

## 3. Поисковый индекс и BM25 (собственная реализация)

Готовые поисковые индексы не используются (библиотека `rank-bm25` удалена из проекта) — `rag/bm25.py`, около 100 строк.

- **Обратный индекс** `InvertedIndex`: `терм → {номер документа: TF}`, длины документов |d|, avgdl, N.
  Фрагмент (`python -m rag stats`):

  | Терм | DF | IDF | Документы (TF) |
  |---|---|---|---|
  | ветка | 5 | 3,31 | git-5 (4), git-6 (3), git-7 (3), git-8 (1), git-9 (2) |
  | процесс | 6 | 3,14 | linux-22, linux-23, linux-24, network-8, powershell-0, powershell-1 |
  | контейнер | 7 | 3,00 | docker-0, docker-1, docker-4, docker-5, docker-6, docker-7, docker-13 |
  | файл | 29 | 1,63 | git-1, git-4, …, linux-5, … |

- **IDF** — по формуле методички: IDF(t) = ln(1 + (N − DF(t) + 0,5) / (DF(t) + 0,5)); всегда положителен,
  поэтому частый терм не может уменьшить оценку.
- **BM25(q, d)** = Σ_{t∈q} IDF(t) · TF(t,d)·(k1+1) / (TF(t,d) + k1·(1 − b + b·|d|/avgdl)).
  Запрос — кортеж термов: повторённый терм учитывается повторно, как в формуле.
- **Поиск идёт по спискам документов индекса**, а не перебором всего корпуса: оценки считаются только для документов,
  где есть хотя бы один терм запроса. Документы без совпадений в выдачу не попадают — это и есть ответ «ничего не найдено».
- Сортировка — по невозрастанию BM25, при равных баллах — по ID в естественном порядке (категория, затем номер:
  `docker-2` раньше `docker-10`), поэтому результат детерминирован.
- Индекс строится в памяти при запуске; приложение пересобирает его само, если файлы `data/corpus/` изменились
  (правка администратора, новый датасет) — `SearchEngine.is_stale()`, `app.search.get_engine()`.
- Для объяснимости `BM25.explain` раскладывает оценку на вклады термов (tf, idf, слагаемое) — их видно в `python -m rag search`.
- Корректность проверена тестами (`rag/tests/test_bm25.py`): на трёх документах из примера методички индекс совпадает
  с таблицей раздела 1.4 (граф → d1, d2; матрица → d2, d3 …), а IDF и BM25 — с ручным расчётом по формулам.

**Параметры:** k1 = 1,2, b = 0,75 — стандартные значения (методичка: k1 ∈ [1,2; 2,0], b = 0,75 на практике).
Сетка k1 × b (MRR) почти плоская — от 0,762 до 0,809:

| k1 \ b | 0 | 0,25 | 0,5 | 0,75 | 1 |
|---|---|---|---|---|---|
| 0,9 | 0,809 | 0,796 | 0,797 | 0,797 | 0,797 |
| **1,2** | 0,788 | 0,775 | 0,776 | **0,777** | 0,781 |
| 1,5 | 0,777 | 0,775 | 0,776 | 0,776 | 0,776 |
| 2,0 | 0,774 | 0,762 | 0,774 | 0,774 | 0,768 |

Различия в пределах ±0,03 на 46 запросах — это шум (один запрос меняет MRR на ~0,02). Брать максимум сетки значило бы
подогнать параметры под тестовый набор, поэтому оставлены стандартные значения. Нормализация длины (b) почти не влияет:
документы короткие и близкие по длине (11–23 терма).

у `chmod` — словами из сценария 1 спецификации («исполняемый», «скрипт», «файл»).

| | R@1 | R@3 | R@5 | R@10 | MRR | MRR@3 |

Строки «до» и «после» получены в одинаковых условиях: те же 149 команд и id, те же 46 вопросов, та же предобработка,
k1, b и глубина выдачи; отличаются только теги. Полные прогоны и корпус «до» сохранены в `rag/results/`
(`before_tags.txt`, `after_tags.txt`, `corpus_before_tags/`) и проверяются командой `diff` (rag/results/README.md).

Вывод: самый сильный фактор — **словарь корпуса** (теги дают +0,25 MRR: описания команд короткие, 2–7 слов,
и без тегов запросу часто не с чем совпасть). Второй — **лемматизация** (+0,06 MRR, +0,09 Recall@5).
Параметры BM25 и веса полей почти не влияют.

## 5. Тестовый набор запросов

`rag/queries.json` — 46 запросов в 9 темах и 7 запросов не по теме.

- **Формулировки — задачи пользователя своими словами, а не фрагменты текста корпуса**, как рекомендует методичка:
  «скрипт не запускается — не хватает прав», «забрать свежие изменения коллег с сервера», «кто занял порт и какие
  соединения открыты». Слова запросов часто отсутствуют в корпусе («каталог», «программы», «макбук») — это проверка
  устойчивости, а не подгонка.
- **Не меньше трёх релевантных документов на запрос:** 3 — у 26 запросов, 4 — у 17, 5 — у 3. Релевантными считаются
  все команды корпуса, решающие задачу, в том числе из разных категорий: «перезапустить системный сервис» →
  `systemctl` (Linux), `Restart-Service`, `Get-Service` (PowerShell), `launchctl` (macOS).
  Проверка автоматическая — `load_queries()` не примет запрос с меньшим числом релевантных.
- **Равномерное покрытие корпуса:** темы — Файлы 7, Сеть 7, Git 7, Процессы и службы 5, Навигация и система 5, Docker 5,
  SQL 5, Python 3, Права и диски 2; среди релевантных встречаются 134 из 149 команд (90 %), по категориям — от 80 до 97 %:
  docker 13/15, git 19/22, linux 29/30, mac 12/15, network 14/16, powershell 21/22, python 10/12, sql 16/17.
- **Запросы не по теме** («рецепт борща со сметаной», «кракозябра», «как приготовить кофе для гостей» …) проверяют
  ответ «ничего не найдено» (раздел 6).

Прежний бенчмарк `benchmark/` (20 запросов, одна ожидаемая команда, Top-3 accuracy) сохранён для истории: он не подходит
под требования методички (нужны ≥ 3 релевантных и Recall@k/MRR), но показывает тот же сдвиг — на старом поиске
15/20 (75 %), на новом 18/20 (90 %): `python benchmark/run.py` (он вызывает `app.search`, то есть уже `rag/`).

Ограничение: запросы, их релевантность и дополнение тегов выполнял один автор, поэтому оценка может быть оптимистичной.
Для контроля стоит добавить запросы, написанные другим участником команды «вслепую», не глядя в корпус.

## 6. Тип ответа для чата

Поиск решает, что показать пользователю (spec/tech/api.md, «Правила ответа»; `SearchEngine.answer`):

- **nothing** — ни один терм запроса не встречается в корпусе → только сообщение, без команд;
- **found** — лучший документ содержит не меньше половины термов запроса и его оценка BM25 не ниже 5,0 →
  лучшая команда + до 2 похожих;
- **similar** — иначе: «подходящая не найдена, возможно, подойдут…» + до 3 вариантов.

На тестовом наборе: запросы не по теме — 7/7 «ничего»; по теме — 23 found (первая команда релевантна в 21 случае, 91 %),
21 similar (первая релевантна в 12), 2 nothing (q01, q06 — см. разбор ошибок). Порог 5,0 выбран по распределению: у всех
«found» с релевантной первой командой оценка выше 5. Порог покрытия 0,5 отсекает случаи, когда совпало одно общее слово
из длинного запроса.

## 7. Результаты и выводы

| Метрика | Значение | Максимум возможного |
|---|---|---|
| Recall@1 | 0,208 | 0,294 |
| Recall@3 | 0,447 | 0,882 |
| Recall@5 | 0,555 | 1,000 |
| Recall@10 | 0,632 | 1,000 |
| **MRR** (по всей выдаче, как в методичке) | **0,777** | 1,000 |
| **MRR@3** (только top-3: нет релевантного в top-3 → 0) | **0,757** | 1,000 |

MRR приводится в двух вариантах: формула методички не ограничивает глубину выдачи, а для чата, где пользователь видит
только 3 команды, честнее MRR@3 — первая подходящая команда ниже третьего места пользу уже не приносит.
Разница небольшая (0,02): если подходящая команда находится, то почти всегда в top-3.

«Максимум возможного» учитывает, что в top-k помещается не больше k документов: при 3–5 релевантных
Recall@1 не может превысить 1/|R| (в среднем 0,294).

По темам (R@3 / R@5 / MRR): Git 0,56 / 0,64 / 1,00; Сеть 0,49 / 0,61 / 0,90; SQL 0,38 / 0,45 / 0,85; Python 0,61 / 0,93 / 0,83;
Процессы и службы 0,42 / 0,47 / 0,70; Docker 0,50 / 0,57 / 0,68; Навигация и система 0,42 / 0,55 / 0,64; Файлы 0,24 / 0,34 / 0,51.

**Выводы о качестве ранжирования.**
1. **Первый ответ в основном верный: MRR = 0,777 (MRR@3 = 0,757)** — в среднем первая подходящая команда стоит на 1–2
   месте; в 33 из 46 запросов — на первом. Для чата, где показывается лучшая команда и 2 похожих, это главный показатель.
2. **Полнота ниже: Recall@5 = 0,555** — поиск находит одну-две подходящие команды, но не все варианты для разных
   платформ. Причина — лексическое совпадение: команды разных ОС описаны разными словами.
3. **Слабее всего — темы с бытовой лексикой** (Файлы, Навигация): пользователи говорят «каталог», «программы», «макбук»,
   а в корпусе — «папка», «процессы», «macOS».

**Разбор ошибок** (`python -m rag eval --details`):
- *Синонимы, которых нет в корпусе:* q01 «посмотреть, что лежит в каталоге» — ни «каталог», ни «лежать» не встречаются
  (в корпусе «папка», «содержимое») → ничего не найдено; q10 «какие программы сейчас работают» — в корпусе «процессы».
- *Словообразование, которое не снимает лемматизация:* «скопировать» ≠ «копировать» (видовая пара — разные леммы),
  «запаковать» ≠ «упаковка» (q04, q06). Стемминг тоже не помог бы: различаются приставки.
- *Общие слова перетягивают ранжирование:* q34 «запустить приложение в контейнере» — первым идёт `Start-Process`
  («запустить приложение»), q36 «освободить место от старых контейнеров» — `docker run`.
- *Дословное совпадение побеждает смысл:* «сделать файл исполняемым» — первым `which` (в его описании дословно
  «путь к исполняемому файлу»), `chmod` — вторым.

**Что улучшит качество дальше:** словарь синонимов для расширения запроса (каталог → папка, программа → процесс,
скопировать → копировать); дополнение описаний команд; плотный (векторный) поиск по смыслу в сочетании с BM25;
расширение тестового набора запросами других авторов.

## 8. Воспроизведение

    pip install -r requirements.txt
    python rag/evaluate.py --compare           # все таблицы этого отчёта (= python -m rag eval --details --compare)
    python rag/demo.py                         # RAG целиком: поиск → промпт → ответ LLM со ссылками на источники
    python -m rag eval --corpus rag/results/corpus_before_tags   # прогон «до» дополнения тегов
    python -m pytest rag tests                 # проверки индекса, формул, метрик и набора запросов

Подробно о командах и демонстрации — `rag/README.md`.
